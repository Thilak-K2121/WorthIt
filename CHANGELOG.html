2026-11-19 · Fix: discovery timer never stopping

Fixed
  • Symptom: the Live AI Discovery radar kept counting past 300 s, and the navbar "Live" badge stayed on, although the run had finished on the server in about 2 minutes.
  • Root cause: the API sent UTC timestamps without a timezone marker (2026-11-19T17:12:54). Browsers read them as local time, 5 h 30 m early in India. The page's "has my run finished?" check compared that time with the click time, so it could never pass. It only ever worked when the user stayed on the page until the request returned. The same bug showed run times 5 h 30 m off in the logs.
  • Fix (backend): every API datetime is now serialized as explicit UTC (...Z) through a shared UTCDateTime type (14 fields). On startup, runs left RUNNING by a restart or redeploy are marked FAILED with a reason, so nothing waits on them forever.
  • Fix (frontend): completion is now detected by run ID (a new run appears with status COMPLETED or FAILED), with no clock comparison. Elapsed time is computed from the start timestamp. The page stops waiting after 10 minutes, and keeps waiting if only the browser's connection dropped while the server kept working. A timezone-safe parseApiDate helper is used for display.
  • 2 new tests. Full suite: 43 passed.

Added: edit names before and after publishing

  • User suggestions: each pending suggestion in the queue now has editable Brand, Model and Variant fields, prefilled with what the user typed. "Approve with edits" publishes the corrected name, and the card shows the original submission for reference.
  • Any phone, any time: the Catalog Manager list has an Edit button on every row, whether the phone was AI-discovered, user-suggested or added by hand. It renames the phone in place. Approved suggestion cards link there via "Rename in Catalog Manager".
  • New endpoint PATCH /api/v1/admin/products/{id} (brand and/or model). It keeps the dedup key and the search name in sync and clears the cache, so the new name shows everywhere at once. Variants, owner reports and history are untouched.
  • Duplicate protection: a rename or approval that would collide with a different existing phone is refused with a clear message (HTTP 409). A phone can be "renamed" to its own name.

Fixed

  • Approving a suggestion whose name already existed crashed with a database error (HTTP 500). It now returns a clear 409, and the suggestion stays pending so it can be corrected.
  • Security: approving or rejecting suggestions was open to anyone, and approval can now also rename. It now requires the admin key, like the other catalog actions.
  • Deploy crash ModuleNotFoundError: No module named 'psycopg': the Render DATABASE_URL used the postgresql+psycopg:// scheme while only psycopg2 is installed. database.py now normalizes every PostgreSQL URL form to the installed driver.

2026-11-17 (update) · In-memory cache, unused-column cleanup

AddedChangedRemoved

Changed: cache now lives in server RAM by default

  • The Render workspace hit its free Key Value (Redis) limit, and the existing instance belongs to another project. The cache layer is now pluggable, selected by CACHE_BACKEND: auto (default: Redis if REDIS_URL is set, otherwise RAM), memory, redis, off.
  • RAM backend (MemoryCache): thread-safe LRU with per-entry TTL and a byte budget (CACHE_MAX_MB, default 64 MB, well inside Render's 512 MB). Least-recently-used entries are evicted once the budget is reached, so the cache cannot exhaust the instance's memory.
  • Everything else is unchanged: the same endpoints, the same invalidation on every write, the same X-Cache / X-Process-Time-Ms headers, and the same admin stats/flush panel (it now also shows RAM used).
  • Trade-offs vs Redis: the cache is per process and empties on restart or spin-down; the first request afterwards is a MISS. This is correct here because the Dockerfile runs a single uvicorn worker. If the backend is ever scaled to several workers or instances, switch to Redis by setting REDIS_URL.
  • Tests run every cache scenario against both backends, plus dedicated TTL, LRU-eviction and byte-budget tests.

Added: "What Owners Actually Paid" on the phone page

  • ownerships.purchase_price was stored but never shown, and the form had no input for it, so only seed data had prices. It is now surfaced instead of being removed.
  • Phone page: a new card shows the average and median price paid, the range, and how far owners paid above or below launch price.
  • Fair comparison: each owner is compared against the launch price of the exact variant they bought (e.g. 12 GB/256 GB vs 12 GB/256 GB), so buying a higher-storage model isn't counted as a markup. Owners who skipped the variant still count toward the average, but not toward the launch comparison.
  • Share Experience form, step 1: new optional "Which variant?" picker (shows each variant's launch price) and "Price you paid (₹)" field.
  • The backend ignores a variant_id that belongs to a different phone, so a mismatched variant can't skew the comparison.
  • API: GET /products/{id}/insights now includes a price_paid object. It is served from the cache and refreshed whenever a new ownership is added.
  • 3 new tests (stats math, empty state, foreign-variant guard). Full suite: 33 passed.

Removed: 23 unused database columns

Each column was traced through the backend logic, the API schemas, the seed data and every React component. A column was removed only if no screen displays it and no logic reads it. Most were either never written, or written with a constant, a default or a value copied from another column.

2026-11-17 · Redis caching, admin catalog management, UI cleanup

Superseded in part: Redis was swapped for an in-memory cache in the update above, so this section's production run and resume bullets no longer apply.

AddedFixedRemoved

Added: Redis read-through response cache

  • New module backend/app/core/cache.py. It caches the fully serialized JSON for the six hot read endpoints: catalog list, brand list, product detail, longitudinal insights, experience reports and side-by-side compare.
  • A cache hit returns the stored bytes directly. It skips the SQL queries, ORM hydration and Pydantic serialization.
  • Write invalidation: every write that can change catalog data clears the cache namespace (worthit:v1:*) with non-blocking SCAN + UNLINK. The writes covered are product create, admin add/delete, ownership registration, experience report, suggestion review, discovery runs and app startup seeding. TTL (default 600 s) is a second safety net.
  • Fail-open + circuit breaker: if REDIS_URL is unset or Redis is unreachable, the API serves from PostgreSQL as before. After an error, Redis is skipped for 30 s so a dead cache never adds timeout latency. Verified by stopping Redis mid-run: requests kept returning 200.
  • Error responses (404/400) are never cached.
  • Diagnostics: every response carries X-Process-Time-Ms. Cached endpoints also carry X-Cache: HIT | MISS | BYPASS | OFF. Sending X-Cache-Bypass: 1 forces the database path (used for A/B benchmarks).
  • Admin cache panel: connection status, hit/miss ratio, cached key count, and a "Flush cache" button.
  • New env vars: REDIS_URL, CACHE_TTL_SECONDS. A redis service was added to docker-compose.yml.

Added: admin catalog management (manual add/delete)

  • AI discovery still writes straight to the database. Admins can now curate the results:
    • Catalog Manager tab in the Discovery console: add a phone by hand (brand, model, release date, market, URL, description, multiple RAM/storage/chipset/price variants), and search all entries and delete any of them.
    • Each AI-discovered phone card in the run logs now has a delete button.
  • New endpoints under /api/v1/admin: GET /verify, POST /products, DELETE /products/{id}, GET /cache/stats, POST /cache/flush.
  • Manual adds go through the same Jaccard deduplication as the AI pipeline. Duplicates are rejected with HTTP 409.
  • Delete cascades to variants, source citations, ownerships and their experience reports. The confirmation dialog warns how many owner records will go.
  • Security: admin routes require an X-Admin-Key header matching ADMIN_API_KEY (constant-time compare). In production they fail closed (HTTP 503) if the key isn't configured. The console asks for the key once and keeps it in the browser's localStorage.

Removed

  • The non-functional "Sign In" button in the navbar. The app has no user accounts; it only linked to /products.

Fixed

  • frontend/src/services/api.js: fetchJson spread options after headers, so any caller passing custom headers silently lost Content-Type: application/json. JSON bodies were then rejected with a 422. This was latent until the admin calls began sending headers.

Tests

  • New backend/tests/test_cache_and_admin.py (11 tests, uses fakeredis). It covers MISS→HIT, bypass, write invalidation, errors not cached, Redis-off and Redis-down fail-open, admin delete + cascade, duplicate rejection, key enforcement, and fail-closed in production.
  • Full suite: 22 passed (11 existing + 11 new).
